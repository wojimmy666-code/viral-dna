# Phase 2 Batch 4.8：爆款洞察与复刻决策工作台

## 1. 目标

分析报告不只回答“视频里有什么”，还要回答以下创作决策问题：

1. 哪些可观察事实构成了视频的开场钩子、留存推进和结尾兑现；
2. 这些事实可能通过什么机制影响点击、留存、互动或分享；
3. 复刻时必须保留哪些“内容 DNA”，哪些人物、服装、产品或场景可以替换；
4. 如何在不照搬表层素材的前提下，生成忠实复刻、差异化同构、强化改进三套新视频方案；
5. 如何把选中的新方案无损发布到现有创作方案工作流。

本功能所有“流量效果”均属于基于内容证据的推断。缺少平台播放、完播、互动等真实指标时，界面必须明确显示“内容推断，不等同于真实平台表现”，不得把推断表述为已验证结论。

## 2. 本批次范围

### 第一部分：爆款洞察领域层

- 建立独立的数据契约、规则引擎、服务、路由与持久化表；
- 把现有 VLM 分镜、字幕、对白、OCR、实体和提示词转换为可引用证据；
- 输出内容结论、机制链、逐镜头流量角色、内容 DNA、替换机会和改进建议；
- 将“观察事实”和“机制推断”区分存储；
- 工作区数据库升级到 Schema v8，保存洞察报告与方案批次。

### 第二部分：分析报告 UI 与交互

分析报告使用五个一级页签：

1. **总览**：结论、证据覆盖、最强钩子、复刻难度、内容 DNA；
2. **爆款机制**：按时间顺序展示“事实 → 机制 → 预期作用 → 证据”；
3. **分镜拆解**：保留原分镜详情，并补充每个分镜的流量角色；
4. **复刻与改进**：DNA 锁定、元素替换、三方案生成与比较；
5. **提示词**：继续提供现有可复制、可导出的提示词包。

页面采用单列宽工作区，不增加固定右侧信息栏。证据详情默认折叠，用户需要时再展开；时间点可以跳转到原视频对应位置。

### 第三部分：三套新视频方案

- 用户在“复刻与改进”中选择需要替换的元素并填写新描述；
- 点击生成后一次产出以下三种方案：
  - **结构忠实复刻**：锁定时长、动作、运镜和信息顺序，只替换表层元素；
  - **差异化同构**：保留流量功能，强化新人物、新场景和视觉辨识度；
  - **强化改进版**：前置核心视觉信号、压缩无信息停留、强化结尾兑现；
- 三方案以同一维度比较：受众、保留 DNA、改进项、难度、成本等级、风险和逐镜头提示词；
- 选中方案后发布为现有“创作方案”，逐镜头图片提示词、视频提示词和负面约束同步写入生产工作流。

## 3. 不在本批次范围

- 不读取或声称拥有真实平台播放、完播、点赞、评论或分享数据；
- 不自动发布视频；
- 不自动替用户决定最终方案；
- 不在本阶段增加账号分析；
- 不把爆款洞察逻辑写入 `ProductionService`；
- 不强制调用新的付费大模型。当前先交付零额外成本的证据规则基线。

## 4. 架构与物理目录

后端独立目录：

```text
services/api/src/viral_dna_api/viral_insights/
├── contracts.py   # 领域契约与 API DTO
├── engine.py      # 可替换的证据规则基线
├── service.py     # 用例编排与仓储/发布端口
├── publisher.py   # 对现有 ProductionService 的窄适配器
└── routes.py      # HTTP 路由
```

前端独立目录：

```text
apps/web/src/viral-report/
├── ViralExecutiveSummary.jsx
├── ViralMechanismWorkspace.jsx
├── ReplicationWorkspace.jsx
├── ConceptComparison.jsx
├── viral-report-ui.js
├── viral-report.css
└── index.js
```

边界原则：

- `engine.py` 只接收分析报告并返回领域契约，不访问数据库和 HTTP；
- `service.py` 只依赖仓储 Protocol 和发布 Protocol；
- `publisher.py` 是唯一知道创作方案内部 API 的文件；
- 前端组件通过注入的 `request` 函数访问 API，不依赖 `App.jsx` 内部状态实现；
- 未来接入百炼推理时增加新的 generator adapter，不修改页面和持久化契约。

## 5. 证据与判断模型

### 5.1 证据引用

每条机制可以引用以下证据：

- 关键帧和证据帧；
- 分镜起止时间；
- 字幕；
- 对白；
- OCR 画面文字；
- 未来接入的真实平台指标。

### 5.2 判断层级

- `observed`：视频中直接可观察或可读取的事实；
- `inferred`：从事实推导出的机制、预期作用和建议；
- `performance_supported`：未来存在真实平台指标且完成校验后才可使用；
- 当前版本默认 `content_inference`。

### 5.3 输出对象

- `ViralInsightReport`：一条分析版本对应一份最新洞察；
- `ViralMechanism`：事实、机制、作用维度、置信度与证据；
- `ViralShotRole`：逐镜头流量角色、贡献、必须保留与可替换项；
- `ViralDNA`：跨方案必须保持的机制与可变变量；
- `ViralReplacementOpportunity`：实体替换建议与风险；
- `ViralImprovement`：有优先级的改进建议；
- `ViralConceptSet`：一次生成的方案批次；
- `ViralConcept`：一套可发布的完整新视频方案。

## 6. API

| 方法 | 路径 | 用途 |
|---|---|---|
| GET | `/api/v1/analyses/{analysis_id}/viral-insight` | 读取洞察；分析报告指纹变化时自动重新生成 |
| GET | `/api/v1/analyses/{analysis_id}/viral-concepts/latest` | 读取最近一次三方案结果 |
| POST | `/api/v1/analyses/{analysis_id}/viral-concepts` | 按替换清单生成方案 |
| POST | `/api/v1/viral-concept-sets/{set_id}/concepts/{concept_id}/publish` | 发布到创作方案 |

## 7. UI 状态与交互

### 7.1 总览

- 首屏显示一句结论，不显示大而空的评分仪表盘；
- 显示“内容推断”标签、证据覆盖率、置信度和复刻难度；
- 内容 DNA 使用“必须保留 / 可替换 / 风险”三组信息；
- 点击“查看机制证据”进入爆款机制页签。

### 7.2 爆款机制

- 按时间排列机制，不按同尺寸卡片网格排列；
- 每行左侧显示时间与流量作用，右侧展示事实、机制与建议；
- 证据默认折叠；展开后显示关键帧、字幕或 OCR 来源；
- 点击时间按钮回到总览视频并跳转对应位置。

### 7.3 复刻与改进

- DNA 锁定项只读，避免用户无意破坏核心机制；
- 替换元素按人物、服装、场景、产品和道具分组；
- 参考资产不是进入下一步的必填项；
- 未填写替换值也能生成结构方案；
- 生成按钮明确说明“生成三套方案，不调用视频模型”；
- 方案生成期间显示局部进度，不阻塞报告其他页签。

### 7.4 方案比较

- 首层使用三列比较摘要；窄屏改为横向滚动或单列；
- 三套方案必须由独立策略生成器构建，而不是共用一份结论后只替换标题；
- 摘要明确显示策略目标、制作难度、成本等级和改动幅度；
- 选中方案后再展开逐镜头详情，避免一次展示全部提示词；
- “创建创作方案”是明确的人工动作；成功后切换到创作方案工作区并选中新项目；
- 创建失败保留当前表单和方案结果，允许重试。

#### 7.4.1 三套独立策略契约

`replication-rules-v2` 将策略实现物理隔离为三个 Builder：

- **结构忠实复刻**：保留镜头顺序、时长、动作方向、运镜轨迹和转场落点，只应用明确的元素替换；
- **差异化同构**：保留钩子、留存和兑现的功能顺序，主动重写人物、场景、构图与视觉记忆点；
- **强化改进版**：只锁定证据支持的核心因果链，前置视觉信号、压缩低信息停留并强化结果兑现。

每个 Builder 必须独立产出：有效性说明、DNA 保留策略、重点改进、制作风险、逐镜头图片提示词和逐镜头视频提示词。生成结束后由多样性校验器对这六类字段逐项检查；任一字段的三套结果完全相同，整批生成失败并返回可读错误，不能把重复方案保存为成功结果。

方案契约升级为 `viral-dna-concepts-v2` / `strategy-contract-v2`。既有 v1 批次不自动删除，仍可作为历史参考打开；接口会把它标记为 `stale`，界面提示重新生成，并禁止直接发布为新的创作方案。由此避免旧缓存继续伪装成三套有效策略。

## 8. 成本与模型演进

当前 `evidence-rules-v1` 和 `replication-rules-v2` 不产生新的模型调用，成本记录为 0。它们依赖分析阶段已经生成的 VLM 事实。

未来模型化时实现统一 Generator 接口：

```text
generate_insight(source_report) -> ViralInsightReport
generate_concepts(source_report, insight, selections) -> ViralConceptSet
```

模型适配器必须：

- 输出相同 Schema；
- 保留证据引用，不允许生成无法追溯的“爆款原因”；
- 记录 provider、model snapshot、用量和成本；
- API Key 不可用、余额不足或输出校验失败时返回可读错误；
- 可以回退到规则基线，但界面必须显示实际 generator。

## 9. 数据迁移与兼容

- 工作区 Schema 从 7 升级为 8；
- 新增 `viral_insights` 与 `viral_concept_sets` JSON 表；
- 洞察以 `analysis_id` 为稳定键，重新分析不会覆盖旧分析版本的洞察；
- 方案批次以 UUID 保存，旧批次可重复打开；
- 原 `AnalysisReport.viral_findings` 保留，作为新领域引擎的兼容输入；
- 原“元素替换”和提示词页签保留已有数据接口，新复刻页统一承接后续替换决策。

## 10. 验收标准

1. 打开已完成分析后可看到新的“内容推断”总览和证据覆盖信息；
2. 每条爆款机制至少能定位到一个分镜证据；
3. 分镜页能看到流量角色、贡献、必须保留和可替换信息；
4. 参考资产为空时仍可进入复刻与改进并生成方案；
5. 可分别填写人物或场景替换描述；
6. 一次生成忠实复刻、差异化同构、强化改进三套方案；
7. 三套方案的有效性说明、DNA、重点改进、风险以及逐镜头图片／视频提示词均存在策略级差异；
8. 切换三套方案时策略目标、摘要和逐镜头提示词同步变化；
9. 旧 v1 批次显示过期原因，不能直接创建创作方案，可一键重新生成；
10. 发布任一当前方案后，创作方案数量增加并自动打开新方案；
11. 新创作方案逐镜头提示词与所选方案一致；
12. 重新打开分析记录后洞察和最近一次当前方案仍存在；
13. 页面明确提示内容推断不等于真实平台表现；
14. 无需额外 API Key 即可完成本轮全流程。
