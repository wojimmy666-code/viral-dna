# 升级、备份与恢复

状态：现行运维要求；尚未在真实服务器执行恢复演练。备份存在不等于已经验证可恢复。

## 1. 升级前

1. 确认维护窗口，等待真实分析、生成、同步和导出完成；不要只因页面关闭就认定任务已经停止。
2. 记录当前应用提交号、Python／Node 与已安装依赖版本、运行服务的系统账户和实际数据路径。秘密值不写入记录或 Git。
3. 停止本项目的 API 及相关写入任务，阻止其他部署实例继续写同一批数据库。
4. 做一致性备份，再准备独立的新发布目录。不要在运行中的代码目录覆盖升级，也不删除旧虚拟环境冒充修复。

## 2. 必须一起备份的内容

| 内容 | 原因 |
| --- | --- |
| 身份库 `accounts.sqlite3` 或配置的认证路径 | 账户、成员、会话、邀请、租约及审计 |
| 账户／设备目录与旧工作区配置 | 保持历史账户 ID、设备 ID、工作区和路径映射 |
| 每个账户完整工作区 | 项目、资产、原视频、历史、导出及引用关系 |
| `.viraldna/workspace.db` 与 `.viraldna/durable-storage.sqlite3` | 业务状态、容量、历史登记、上传断点与同步收据 |
| `objects/durable/` 及其余账户媒体目录 | 独立长期原件以及仍被业务引用的文件，不能只备份最终采用图 |
| API 配置、通知／偏好／平台连接配置与受控秘密存储 | 运行环境及连接信息；按敏感备份管理 |

优先采用停写后备份整个相关数据集，或经验证的 SQLite 在线备份流程。运行中不能只复制 `.db` 主文件而忽略 WAL；身份库、业务库和存储库必须处于一致的可恢复时间点。不要把媒体目录中的硬链接数当成业务引用计数。

备份放在独立磁盘或独立备份服务；仅复制到同一磁盘另一个目录不能覆盖磁盘损坏风险。设置保留周期与访问控制，不把备份、Cookie、激活链接或密钥提交到 GitHub。

## 3. Windows 凭据的恢复边界

平台 Cookie、媒体暂存及同步连接相关秘密存储使用 Windows DPAPI。仅拷贝密文文件，不保证在另一台机器、另一个 Windows 用户或 Linux 上可解密。

- 同机恢复也应保持原运行身份并验证解密。
- 异机／异用户恢复后，准备由负责人重新授权平台连接、重新绑定同步账户及按需配置凭据。
- 不能为了恢复而把密钥改成明文存储，或禁用身份校验。
- 原账户 ID、设备映射与资产索引继续保留；需要重新授权不等于需要重新初始化账户。

## 4. 发布新版本

1. 使用经审核的版本和依赖，在新目录安装并构建；GitHub 访问统一通过 SSH。
2. 先在隔离数据副本验证新版本，测试期间不连接真实付费模型，不向真实服务器同步。
3. 维护窗口内将服务配置切到新版本，保留已核实的数据目录和系统账户。
4. 仅启动一个 API 进程；检查健康、登录、账户隔离、媒体读取、容量与任务状态，再恢复写入。
5. 最后刷新前端，确认静态文件与 API 版本匹配。后台清点未完成时耐心等待，不重复初始化或清空账本。

## 5. 回滚与恢复

数据库／工作区 Schema 可能在启动时升级。代码回滚不等于数据格式自动降级，不应把旧程序直接连到未经验证的新 Schema。

若发布失败，先停止写入并保全升级后的数据及新产生的文件，再评估兼容性。只有确认兼容时才单独回退应用；否则需要恢复与旧版本匹配的一致性备份，并明确处理维护窗口后新增的数据，不能静默覆盖它们。

恢复先在隔离目录验证：账户能登录、两个账户仍隔离、项目与采用记录完整、历史原件可下载、哈希一致、容量与引用检查正确。验证通过并取得切换许可后，再恢复正式服务。

## 6. 日常检查

- 监控物理磁盘、账户逻辑额度、预留量和同步失败；临时文件、备份和缓存也需要物理空间。
- 历史没有自动过期策略；用户删除须走回收站与引用检查，管理员不能通过定时清空媒体目录“释放容量”。
- 定期做恢复演练，记录应用版本、备份时间、恢复用时及结果，不把计划中的检查写成已通过。
- 发现任务中断时先核对已有输出与可恢复状态，避免盲目重复提交付费任务。
