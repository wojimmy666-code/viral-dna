# 服务器部署

状态：根据当前代码核对的部署流程，尚未完成真实目标服务器验收。Windows 已提供 [正式部署菜单与服务配置](Windows服务器一键部署.md)；其他环境仍需确定对应服务管理方式。域名、服务账户及实际部署结果须在目标服务器验收。本文件不创建云资源或执行部署。

## 1. 发布边界

- API：FastAPI／Uvicorn，当前使用单个进程；不使用 `--reload` 或多个 worker。
- Web：构建后的静态文件由 HTTPS Web 服务器提供；浏览器的 `/api/v1` 请求转发到同域 API。
- 账户数据库、工作区、存储账本和原件必须在持久磁盘，不放进会被新版本覆盖的代码／构建目录。
- 本地 Windows 启动链已有代码和测试依据；Linux 上的应用接收端、本机工具和凭据能力必须分别验收，不能将可安装 Python 等同于全功能兼容。DPAPI 依赖见 [备份恢复](升级备份与恢复.md)。

## 2. 准备经过审核的代码版本

Windows `C:\Projects\ViralDNA` 单目录、先复制工具再拉取 Git、由 IIS 提供入口的具体流程见 [当前账户服务器工具包](当前账户服务器工具包.md)。它会处理已含 `.server` 的非空目录，不能直接对该目录使用普通 `git clone`。

GitHub 传输统一使用 SSH，远程固定为 `git@github.com:wojimmy666-code/viral-dna.git`。默认在 `main` 开发，不为部署自动创建分支或推送。

首次准备独立部署目录时可用：

```text
git clone git@github.com:wojimmy666-code/viral-dna.git
```

发布前记录实际提交号及依赖版本。不要对含未提交修改或运行中业务数据的目录直接执行更新；后续发布按 [升级流程](升级备份与恢复.md) 操作。

## 3. 分离配置与数据

由固定系统账户运行服务，并确认该账户对配置及持久数据目录的读写权限。Windows 单账户部署可直接使用当前登录的管理员，不需要新建服务用户，详见 [当前账户服务器工具包](当前账户服务器工具包.md)。以下字段应使用实际的绝对路径；迁移旧系统时沿用已核实的路径，不临时生成新账户目录冒充原数据。

| 配置 | 用途 |
| --- | --- |
| `VIRAL_DNA_ENV_FILE` | API 独立配置文件；通过服务进程环境设置 |
| `VIRAL_DNA_AUTH_MODE=password` | 正式账户认证，不切换到免登录模式 |
| `VIRAL_DNA_ADMIN_CONSOLE_ENABLED=true` | 独立 admin 后台 |
| `VIRAL_DNA_ACCOUNT_CATALOG_PATH` | 账户／设备／工作区目录文件 |
| `VIRAL_DNA_AUTH_DB_PATH` | 身份、会话、邀请和编辑租约数据库 |
| `VIRAL_DNA_ACCOUNTS_ROOT` | 新账户工作区父目录 |
| `VIRAL_DNA_WORKSPACE_ROOT` | 首次绑定的旧工作区；不是用户可切换空间 |
| `VIRAL_DNA_PLATFORM_SECRET_ROOT` | 受控凭据目录；不能公开静态映射 |
| `VIRAL_DNA_CORS_ORIGINS` | 精确前端源站；初始设置时需允许所用本机来源 |

Windows 默认目录常与运行服务的系统账户有关。由交互用户改为系统服务用户后，默认 `%LOCALAPPDATA%` 和 DPAPI 身份可能改变，因此必须显式核对，不能仅验证端口启动。

目标服务器只是接收本地同步时，不需要把 `VIRAL_DNA_SYNC_SERVER_URL` 指向自己；该字段配置在发送端，指向另一台 ViralDNA 服务器。

## 4. 安装与构建

依赖依据 [API 清单](../../services/api/pyproject.toml) 与根 `package-lock.json`；在新发布目录建立独立 Python 虚拟环境，安装项目后构建前端：

```text
npm ci
python -m venv .venv
```

使用此虚拟环境的 Python 执行 `-m pip install -e services/api`；需要 ASR／OCR 时增加 `local-ai` 可选依赖。Windows 命令示例见 [本地环境](本地环境与启动.md)。

```text
npm run build:web
```

实际 Web 静态目录是 `apps/web/dist/client/`，不是源码目录，也不是整个仓库。构建还保留既有 Sites 交付产物；本流程不发布 Sites，静态前端也不能替代带持久磁盘的 API。

前端默认 API 基址为 `/api/v1`。部署前确认构建环境没有把 `VITE_API_BASE_URL` 固定到开发机。

## 5. 初始设置与常驻服务

先仅在部署本机启动，完成 [账户初始化](账户初始化.md) 后再开放公网入口。下面是同机反向代理场景的 API 命令模板，其中 `python` 必须指向该发布目录的虚拟环境解释器：

```text
python -m uvicorn viral_dna_api.main:app --app-dir services/api/src --host 127.0.0.1 --port 8000 --workers 1 --proxy-headers --forwarded-allow-ips 127.0.0.1
```

由部署环境的服务管理器维护固定工作目录、系统账户、环境变量、开机启动、日志和受控停止。代理不在同机时须按真实拓扑配置绑定和受信代理地址；不要把 `--forwarded-allow-ips` 设为任意来源。

## 6. HTTPS 反向代理检查表

- 静态站点支持 SPA 回退：`/login`、`/admin/login`、项目 URL 刷新仍能进入前端。
- `/api/` 转发时保留完整路径，不能剥离 `/api`；正确传递公开 Host、HTTPS scheme 和真实客户端来源。
- 公网只开放受控的 HTTPS 入口，API 8000 不直接暴露；受信代理之外的请求不能伪造 HTTPS。
- 不公开映射工作区、身份库、`.env.local`、秘密存储或媒体原件目录；私有媒体由应用授权访问。
- 同步分块至少允许 4 MiB，批次清单至少允许 8 MiB；普通视频上传还需按应用上传限制配置更大的请求体上限。
- 不截断流式响应；为大文件上传／下载与长连接配置合适的超时。不要把生成任务的后台运行等同于必须保持一个同步 HTTP 请求。

具体 Web 服务器的可执行配置应在目标环境确定后验证，再作为该部署实例的附件保存，不复制未经验证的通用配置冒充实测结果。

## 7. 上线验收

1. 本机 `/health` 返回 ViralDNA 健康结构；公网域名与证书正确。
2. 前端与 admin 分别登录；未登录不能读私有资产，两个账户不能串数据。
3. 同企业两个用户争用项目时仅一方可编辑；其他人只读。
4. 使用少量测试文件完成上传、断线恢复、内容校验、历史预览和下载。
5. 后台修改容量生效，超额提示正确，已存在文件不因超额被删除。
6. 受控重启后账户、工作区、同步任务和生成历史仍在。
7. 完成独立备份及一次恢复验证，再安排真实资产首次迁移。

此清单目前是待执行的服务器验收，不等同于本地隔离测试已覆盖真实网络、磁盘和代理环境。
